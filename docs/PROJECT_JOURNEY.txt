5. MCP SERVER — THE FOUNDATION
--------------------------------
  Built an MCP server with 5 intent-based tools:

    capture_task   → Create a new task from natural language
    review_task    → List, search, and filter tasks
    modify_task    → Update existing task fields
    resolve_task   → Mark a task as completed
    remove_task    → Delete a task permanently

  Tech: Python 3.12, FastMCP, Streamable HTTP transport, InMemoryTaskStore
  Docs: spec/mcp/ — transport, tools, implementation plan, testing, roadmap


6. DOCKER + CI + REGISTRY — AUTOMATION
---------------------------------------
  Created multi-stage Dockerfiles + CI workflows for both services:

  MCP SERVER:
    - Dockerfile: services/task-mcp/Dockerfile (builder + runtime, HEALTHCHECK)
    - Workflow: .github/workflows/task-mcp-build.yml (triggers on services/task-mcp/**)
    - Image: ghcr.io/asifalishaikh/task-manager-agent/task-manager-mcp

  SANDBOXAGENT:
    - Dockerfile: services/task-manager-agent/Dockerfile (builder + runtime)
    - Workflow: .github/workflows/task-agent-build.yml (triggers on services/task-manager-agent/**)
    - Image: ghcr.io/asifalishaikh/task-manager-agent/task-sandbox-agent

  Chose GitHub Container Registry (ghcr.io) over Docker Hub because:
    * Unlimited private repos (Docker Hub limits to 1)
    * Native CI + registry integration — same repo, same GITHUB_TOKEN
    * Permissions inherit from GitHub repo access automatically
    * Images appear under "Packages" section on the GitHub repo page

  Note: This is CI + delivery to registry only. Full CD (auto-deploy to
  a live server like K8s) will be added in Part 3.


7. OPENAI AGENTS SDK — RESEARCH
---------------------------------
  Studied the SDK documentation to understand two agent types:

  AGENT (Simple):
    - Core building block with instructions, tools, MCP, handoffs, guardrails
    - Works with any LLM via LiteLLM
  
  SANDBOXAGENT:
    - Extends Agent with workspace isolation
    - Adds Filesystem, Shell, Skills, Memory, Compaction capabilities
    - Uses DockerSandboxClient for container-level isolation
    - Bridges to Kubernetes deployment

  DECISION: Use Simple Agent now, SandboxAgent for K8s later
  DOCS: docs/adrs/agent-decision.md, spec/agents/sandbox-agent-spec.md

APPENDIX: HOW THE AGENT USES MCP TOOLS IN PART 1
-------------------------------------------------

  The Task Manager Agent is the "brain" — it decides which MCP tool to call
  based on user input. The MCP Server just executes the tool and returns data.

  Flow:

    User: "Create a task: Buy groceries"
            ↓
    Agent (LLM) understands intent
            ↓
    Agent calls MCP tool → capture_task(title="Buy groceries")
            ↓
    MCP Server processes → saves to InMemoryTaskStore
            ↓
    Returns result to Agent
            ↓
    Agent replies: "✅ Task created: Buy groceries"

  All 5 tools work the same way — user says what they want → agent picks
  the right tool → MCP executes → agent responds.

    capture_task   →  "Save this task"
    review_task    →  "Show me all tasks"
    modify_task    →  "Change the title"
    resolve_task   →  "Mark this done"
    remove_task    →  "Delete this task"

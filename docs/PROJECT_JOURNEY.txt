5. MCP SERVER — THE FOUNDATION
--------------------------------
Built an MCP server with 5 intent-based tools:

  capture_task   → Create a new task from natural language
  review_task    → List, search, and filter tasks
  modify_task    → Update existing task fields
  resolve_task   → Mark a task as completed
  remove_task    → Delete a task permanently

  Tech stack: Python 3.12, FastMCP, Streamable HTTP transport, InMemoryTaskStore
  Documentation: spec/mcp/ — transport, tools, implementation plan, testing, roadmap

  Each tool accepts natural language input and returns markdown-formatted results
  optimized for LLM consumption. The tools are intent-based — they capture what
  the user means, not just literal commands.

---------------------------------------
Multi-stage Dockerfiles and CI workflows were created for both services:

    - Image: ghcr.io/asifalishaikh/task-manager-agent/task-sandbox-agent
    - Triggers: services/task-manager-agent/** changes

  Registry choice — GitHub Container Registry (ghcr.io) over Docker Hub:
    - Unlimited private repositories (Docker Hub limits to 1)
    - Native CI/CD integration — same repo, same GITHUB_TOKEN
    - Permissions inherit from GitHub repo access automatically
    - Images appear under "Packages" section on the GitHub repo page

  Note: This is CI + delivery to registry only. Full CD (auto-deploy to a
  live server like K8s) will be added in Part 3.


7. OPENAI AGENTS SDK — RESEARCH
---------------------------------
Studied the SDK documentation to compare two agent types:

  AGENT (Simple Agent):
    - Core building block with instructions, tools, MCP, handoffs, guardrails
    - Works with any LLM via LiteLLM provider

  SANDBOXAGENT:
    - Extends Agent with workspace isolation
    - Adds Filesystem, Shell, Skills, Memory, Compaction capabilities
    - Uses DockerSandboxClient for container-level isolation
    - Bridges directly to Kubernetes deployment

  Decision: Simple Agent for immediate CLI use, SandboxAgent for K8s deployment
  Documentation: docs/adrs/agent-decision.md, spec/agents/sandbox-agent-spec.md

9. KEY ARCHITECTURAL INSIGHT — HOW AGENT USES MCP
----------------------------------------------------
  The Task Manager Agent is the "brain" — it decides which MCP tool to call
  based on user input. The MCP Server executes the tool and returns data.
  The agent never stores or manages tasks directly — it delegates to MCP.

  Flow:
    User: "Create a task: Buy groceries"
        |
    Agent (LLM) understands intent
        |
    Agent calls MCP tool → capture_task(title="Buy groceries")
        |
    MCP Server processes → saves to InMemoryTaskStore
        |
    Returns result to Agent
        |
    Agent replies: "Task created: Buy groceries"

  All 5 tools follow this same pattern:
    capture_task   → "Save this task"
    review_task    → "Show me all tasks"
    modify_task    → "Change the title"
    resolve_task   → "Mark this done"
    remove_task    → "Delete this task"

2. CI PACKAGE PERMISSION LESSON
---------------------------------
  A critical learning experience with GitHub Container Registry permissions:

  MCP Server (worked first time):
    - Created Dockerfile + CI workflow → pushed to GitHub
    - CI ran and created the package on ghcr.io automatically
    - GITHUB_TOKEN (repo-scoped) had full write access

  SandboxAgent (failed 3 times):
    - The image was pushed FROM LOCAL MACHINE FIRST using a personal token
    - This created a USER-SCOPED (private) package on ghcr.io
    - When CI tried to push, GITHUB_TOKEN received: permission_denied: write_package
    - Personal tokens can create user-scoped packages, but CI's GITHUB_TOKEN
      can only write to REPO-SCOPED packages — not user-scoped ones

  Resolution:
    1. Deleted the user-scoped package via GitHub web UI:
       Package settings → Delete this package → Confirm
    2. Created a fresh image name that had no existing package
    3. Pushed the workflow first (no local push) → CI created the package
       as repo-scoped automatically
    4. Every subsequent push (local or CI) worked

  The Rule:
    NEVER push a Docker image from your local machine to ghcr.io before CI
    has created the package. Always let CI create the package first. CI's
    GITHUB_TOKEN can only write to repo-scoped packages, not user-scoped.

    - sleep infinity keeps CLI agent alive for exec access
    - curl added to agent image for in-pod debugging


2. SECRET MANAGEMENT — FROM .ENV TO K8S
-----------------------------------------
  API keys must reach pods securely without touching GitHub. The process:

  Step 1 — The .env file (local machine, in .gitignore):
    GEMINI_API_KEY=ai-xxx...
    OPENAI_API_KEY=sk-xxx...

  Step 2 — Generate secret.yaml from .env:
    kubectl create secret generic task-sandbox-secret \
      --from-env-file=.env \
      --namespace=task-manager \
      --dry-run=client -o yaml > secret.yaml

    This reads every key-value pair from .env, base64 encodes them automatically,
    and writes a ready-to-use K8s Secret YAML.

  Step 3 — Apply to cluster:
    kubectl apply -f secret.yaml

  Step 4 — Protect secret.yaml (add to .gitignore):
    echo "secret.yaml" >> .gitignore

  Why this approach works:
    - .env stays local (never pushed to GitHub)
    - secret.yaml is generated and applied locally (never pushed)
    - Only the K8s cluster stores the encoded secrets
    - For production, replace with Sealed Secrets or External Secrets Operator

  Lesson learned: .env files must have each KEY=VALUE on a single line.
  A line break in the middle of a value creates a malformed YAML complex key
  in secret.yaml. Always verify secret.yaml after generation.

4. ROLE OF EACH YAML FILE
---------------------------
  namespace.yaml
    → Creates an isolated space called "task-manager"
    → All resources go here — easy to manage or delete as a unit

  task-mcp/deployment.yaml
    → Runs the MCP server container
    → 2 replicas for reliability
    → securityContext: runAsNonRoot, runAsUser: 1001
    → Health checks (liveness + readiness probes on port 8000)
    → CPU/memory resource limits

  task-mcp/service.yaml
    → ClusterIP service — gives the MCP pod a fixed DNS name
    → Internal DNS: task-mcp-service.task-manager.svc.cluster.local

  task-mcp/configmap.yaml
    → Non-sensitive settings (LOG_LEVEL, HOST, PORT) injected at runtime

  task-sandbox-agent/deployment.yaml
    → Runs the agent container
    → command: ["sleep", "infinity"] — keeps pod alive for exec access
    → Mounts /var/run/docker.sock → can create sandbox containers
    → Injects GEMINI_API_KEY and OPENAI_API_KEY from Secret
    → securityContext: runAsNonRoot, allowPrivilegeEscalation: false, drop ALL caps
    → No Service needed — CLI tool, not HTTP server
    → Internal DNS to reach MCP via MCP_SERVER_URL env var

  task-sandbox-agent/secret.yaml
    → NOT COMMITTED to GitHub (in .gitignore)
    → Generated locally from .env file
    → Contains base64-encoded API keys

6. APPLY ORDER
---------------
  Apply in this exact order (each step depends on previous):

    1. kubectl apply -f Deployments/k8s/namespace.yaml
    2. kubectl apply -f Deployments/k8s/task-mcp/configmap.yaml
    3. kubectl apply -f Deployments/k8s/task-mcp/service.yaml
    4. kubectl apply -f Deployments/k8s/task-mcp/deployment.yaml
    5. kubectl create secret generic task-sandbox-secret \
         --from-env-file=.env \
         --namespace=task-manager \
         --dry-run=client -o yaml > secret.yaml
       kubectl apply -f secret.yaml
    6. kubectl apply -f Deployments/k8s/task-sandbox-agent/deployment.yaml

  Verify with: kubectl get pods -n task-manager -w


7. FIXES APPLIED DURING SETUP
-------------------------------

  FIX 1 — .env file: OpenAI key was split across two lines due to paste
    formatting. This created a malformed YAML complex key in secret.yaml.
    Fix: merged to single OPENAI_API_KEY=sk-proj-... line, regenerated secret.

  FIX 2 — securityContext: K8s-level enforcement of non-root user.
    Pod-level: runAsNonRoot: true, runAsUser: 1001
    Container-level (SandboxAgent): allowPrivilegeEscalation: false,
    capabilities.drop: ["ALL"]. MCP server has pod-level only.
    Note: allowPrivilegeEscalation and capabilities are container-level
    fields, not pod-level. Putting them under spec.securityContext causes
    "strict decoding error: unknown field".

  FIX 3 — serviceAccountName: Both deployments had
    "serviceAccountName: default" explicitly set. Removed entirely — when
    omitted, K8s uses default SA implicitly. RBAC is unnecessary for
    services that never call the K8s API.

  FIX 4 — curl: Added to SandboxAgent Dockerfile for in-pod debugging.
    curl was not available in the base python:3.12-slim image.
    Fix: apt-get install curl in the runtime stage.

  FIX 5 — Replicas: MCP server increased from 1 to 2 for availability.
